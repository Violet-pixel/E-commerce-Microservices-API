    Visão geral

    Como os dados estão divididos entre os serviços e as convenções usadas em todos os bancos.

    Um banco por serviço

    O Cesto segue o padrão database per service: cada microsserviço é o único dono do seu banco. Assim cada parte pode evoluir, escalar e ter backup separadamente, e uma mudança de tabela não quebra outro serviço.

    BancoDonoConteúdo
    cesto_authauthUsuários, clientes OAuth2, códigos, refresh tokens, chaves de assinatura
    cesto_catalogcatalogCategorias, produtos, outbox
    cesto_inventoryinventorySaldos, reservas, outbox, eventos processados
    cesto_ordersordersPedidos, itens, histórico, outbox, eventos processados
    cesto_paymentspaymentsPagamentos, outbox, eventos processados
    cesto_notificationsnotificationsNotificações

    Os seis bancos podem ficar no mesmo servidor PostgreSQL 16 (como no Docker Compose) ou em servidores diferentes. Basta apontar o DATABASE_URL de cada serviço. Cada serviço abre a conexão em src/db.js, com o adapter @prisma/adapter-pg e o cliente Prisma gerado por npm run generate em src/generated/prisma (fora do Git). Esse cliente é gerado em TypeScript e o Node.js 22.18 ou mais novo o carrega direto, removendo os tipos; o resto do código é JavaScript.

    Como os dados se relacionam entre serviços

    Não existem chaves estrangeiras entre bancos. As referências cruzadas são identificadores (product_id, order_id, user_id) mantidos por eventos:

    • products.id do catálogo vira stock_items.product_id no estoque pelo evento product.created.
    • orders.id é referenciado por reservations.order_id, payments.order_id e notifications.order_id.
    • users.id do auth é o sub do JWT e aparece como user_id em pedidos, pagamentos e notificações.
    • Os itens do pedido guardam uma cópia do SKU, do nome e do preço no momento da compra.

    Redis

    O Redis não é fonte da verdade de nenhum dado de negócio, exceto o carrinho, que é descartável por natureza. Ele guarda os fluxos de eventos, o carrinho e os contadores de rate limit.

    Fora do servidor

    Os produtos guardados e o último endereço do checkout, novos na interface 1.2.0, ficam só no navegador, em localStorage: cesto.guardados.<id do usuário> e cesto.endereco. Não há tabela nem chave do Redis para eles.

    Eventos, outbox e Redis

    Como um evento sai do banco, chega ao Redis e é lido pelos outros serviços.

    Outbox transacional

    1. A mudança de negócio e a linha em outbox_events são gravadas na mesma transação.
    2. O relay de cada serviço lê até 100 linhas com published_at IS NULL, em ordem de criação, publica com XADD e marca published_at.
    3. Se o processo cair entre publicar e marcar, a linha é publicada de novo; quem consome descarta a repetição pela tabela processed_events.
    SELECT name, count(*) FROM outbox_events WHERE published_at IS NULL GROUP BY name;
DELETE FROM outbox_events WHERE published_at < now() - interval '30 days';

    Chaves do Redis

    ChaveTipoDonoConteúdo
    cesto:events:<evento>Streamquem publicaEnvelope JSON no campo event; limite aproximado de 100 mil entradas
    cesto:events:dead-letterStreamtodosEventos inválidos ou que falharam 5 vezes, com stream, id, grupo e motivo
    cesto:cart:<userId>HashcartproductId → quantidade; expira em 30 dias sem uso
    cesto:ratelimit:*StringgatewayContadores por IP

    Cada serviço consumidor tem um grupo com o próprio nome (inventory, orders, payments, notifications, cart) em cada stream que lê. A página Serviços da interface mostra se o Redis está respondendo, pelo GET /health do gateway.

    Como preparar o banco

    Com Docker, num PostgreSQL próprio, ao mudar o esquema e na hora do backup.

    Com Docker (recomendado)

    O docker-compose.yml sobe o PostgreSQL 16 e executa docker/postgres/init.sql na primeira vez, criando os seis bancos. Cada serviço roda prisma migrate deploy ao iniciar, com até 10 tentativas enquanto o banco sobe, e depois executa node src/main.js. Não há passo manual.

    PostgreSQL próprio

    CREATE ROLE cesto LOGIN PASSWORD 'troque-esta-senha';
CREATE DATABASE cesto_auth OWNER cesto;
CREATE DATABASE cesto_catalog OWNER cesto;
CREATE DATABASE cesto_inventory OWNER cesto;
CREATE DATABASE cesto_orders OWNER cesto;
CREATE DATABASE cesto_payments OWNER cesto;
CREATE DATABASE cesto_notifications OWNER cesto;

    Depois, com DB_USER, DB_PASSWORD, DB_HOST e DB_PORT no .env:

    npm ci
npm run generate   # gera o cliente Prisma de cada serviço em src/generated/prisma
npm run migrate

    Em servidores separados, defina o DATABASE_URL de cada serviço diretamente no ambiente.

    Mudar o esquema

    1. Edite services/<serviço>/prisma/schema.prisma.
    2. Na pasta do serviço, rode npx prisma migrate dev --name descricao apontando para um banco de desenvolvimento.
    3. Revise o SQL gerado em prisma/migrations/ e acrescente restrições CHECK quando fizer sentido.
    4. Rode npm run generate para atualizar o cliente Prisma e npm test. Como não há compilador, procure no código os usos das colunas alteradas (grep pelo nome em camelCase) e deixe os testes apontarem o resto.
    5. Em produção, prisma migrate deploy aplica as migrações novas ao iniciar o serviço.

    Consultas úteis

    Pedidos e valor total por status:

    SELECT status, count(*), sum(total_cents) / 100.0 AS total FROM orders GROUP BY status;

    Linha do tempo de um pedido:

    SELECT o.number, h.status, h.note, h.created_at
FROM order_history h JOIN orders o ON o.id = h.order_id
WHERE o.number = 1021 ORDER BY h.created_at;

    Produtos com pouco estoque:

    SELECT sku, available, reserved FROM stock_items WHERE available < 5 ORDER BY available;

    Reservas presas há mais de 15 minutos:

    SELECT r.order_id, r.status, s.sku, r.quantity
FROM reservations r JOIN stock_items s USING (product_id)
WHERE r.status = 'HELD' AND r.created_at < now() - interval '15 minutes';
