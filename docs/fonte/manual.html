    Visão geral

    O que é o Cesto, o que ele cobre e com que tecnologias foi feito.

    Para que serve

    O Cesto é uma API de e-commerce dividida em microsserviços e escrita em JavaScript (módulos ES, Node.js 22.18 ou mais novo). Ela cobre o caminho inteiro de uma loja: catálogo, estoque, carrinho, pedido, pagamento e notificações. Junto vem uma interface web em React que usa a mesma API que qualquer outro cliente usaria.

    O projeto tem três usos: base para uma loja real, referência de arquitetura (eventos, saga, outbox, OAuth2, contratos com Zod) e material de estudo. Tudo sobe com um comando e já vem com dados de demonstração.

    O que o Cesto faz

    • Oito serviços independentes, cada um com processo e banco próprios.
    • Pedido como saga: reserva de estoque, cobrança e confirmação. Se uma etapa falha, as anteriores são desfeitas automaticamente.
    • Eventos em Redis Streams com outbox transacional, deduplicação, novas tentativas e fila de dead-letter.
    • OAuth2: Authorization Code com PKCE, Client Credentials, JWT RS256, JWKS e refresh token com rotação e detecção de reuso.
    • Contratos com Zod. O mesmo contrato valida a entrada e a saída, gera o OpenAPI e alimenta o cliente HTTP.
    • Erros de domínio mapeados para HTTP num só lugar.
    • Loja web com catálogo filtrável, produtos guardados, carrinho, checkout em etapas, pedidos com a trilha da saga, notificações, painel administrativo e uma página com a saúde dos serviços.

    Novidades da 1.2.0

    A API, os bancos, as migrações e os eventos continuam iguais aos da 1.1.0. Mudam a linguagem do código e a interface.

    • Todo o código agora é JavaScript. Os oito serviços, os três pacotes e a interface deixaram o TypeScript. Os serviços rodam direto de src/ com node, sem etapa de compilação e sem a pasta dist/; os pacotes exportam src/index.js; os contratos continuam em Zod, com JSDoc nos pontos de entrada. Saíram o typecheck, os tsconfig, o tsc e o tsx; entrou o npm run check. O Node.js 22.18 ou mais novo é o mínimo, porque o cliente Prisma gerado (src/generated/prisma/client.ts) é importado direto pelo Node, que remove os tipos ao carregar.
    • Interface nova. Mesma tipografia do Lume (Literata, Public Sans e IBM Plex Mono), papel cru, verde como única cor de ação e etiquetas de preço de empório. Tema claro e escuro, foco visível em tudo e layout próprio para celular. Os componentes agora são arquivos .jsx.
    • Loja: filtros laterais por seção, faixa de preço e Só com estoque, com os filtros ativos em etiquetas removíveis; busca com atalho /; aviso de Restam N quando o estoque está acabando; visualização rápida do produto com quantidade.
    • Guardados: o coração em cada produto guarda para depois. A lista fica no navegador, separada por conta, e tem Pôr tudo no carrinho.
    • Carrinho e checkout: carrinho em forma de cupom, Guardar tira o item do carrinho sem perdê-lo, e o checkout tem três etapas (Entrega, Pagamento, Revisão) e lembra o último endereço.
    • Pedidos: a saga aparece numa trilha com o serviço que resolveu cada etapa (orders, inventory, payments) e o motivo quando o pedido cai; Comprar de novo devolve os itens ao carrinho.
    • Administração: receita confirmada, ticket médio, pedidos para enviar e produtos com estoque baixo no topo; filtros de pedido, exportação em CSV, busca e filtro de estoque baixo nos produtos.
    • Serviços: página pública que lê /health do gateway a cada 5 segundos e mostra cada serviço, o Redis e o tempo de resposta.

    Os dois manuais em PDF foram refeitos com o mesmo visual, a partir das fontes HTML em docs/fonte/.

    Como rodar

    Da primeira execução com Docker até deixar a loja no ar com HTTPS.

    Requisitos

    Com Docker, basta o Docker com Docker Compose (no Windows, o Docker Desktop). Para desenvolver sem Docker: Node.js 22.18 ou mais novo, PostgreSQL 16 e Redis 7. Os onze contêineres precisam de cerca de 2 GB de memória livre.

    Primeira execução

    1. Baixe ou clone o repositório.
    2. No Windows, dê dois cliques em iniciar.cmd. No Linux ou macOS, rode ./iniciar.sh.
    3. O script cria o .env a partir do .env.example, com uma senha aleatória para o banco e um segredo aleatório para os serviços.
    4. As imagens são construídas e os contêineres sobem: PostgreSQL, Redis, os oito serviços e a interface.
    5. Cada serviço aplica as próprias migrações ao iniciar. O auth cria os clientes OAuth2 e as contas de demonstração, e o catalog publica os produtos de exemplo.
    6. O navegador abre em http://localhost:8080.

    A primeira construção baixa as dependências e leva alguns minutos. As seguintes reaproveitam o cache.

    Contas de demonstração

    PapelE-mailSenhaPode
    Administradoradmin@cesto.devCesto@2026Tudo, incluindo produtos, estoque e expedição
    Clientecliente@cesto.devCesto@2026Carrinho, guardados, pedidos e notificações

    Os nomes, os produtos e o domínio cesto.dev são fictícios. Para trocar a senha das contas de demonstração, altere DEMO_PASSWORD antes da primeira execução.

    Comandos do dia a dia

    docker compose ps                          # estado dos contêineres
docker compose logs -f orders inventory    # acompanhar a saga
docker compose restart payments            # reiniciar um serviço
docker compose up -d --scale inventory=3   # mais consumidores de eventos
docker compose down                        # parar (mantém os dados)
docker compose down -v                     # parar e apagar bancos e Redis

    Desenvolvimento sem Docker

    Com o PostgreSQL e o Redis rodando na máquina e o .env preenchido:

    npm ci
npm run generate          # gera o cliente Prisma de cada serviço
npm run migrate           # aplica as migrações nos seis bancos
npm run dev               # sobe os oito serviços com recarga automática
npm run dev -w apps/web   # interface em http://localhost:5173

    Não há etapa de compilação: npm run dev roda node --watch src/main.js em cada serviço, e npm run start:local roda node src/main.js, sem recarga. A API fica em http://localhost:8000. O único build que resta é o da interface (npm run build, que só existe em apps/web, com o Vite), usado na imagem Docker do contêiner web.

    Uso em produção

    1. No .env, defina SEED_DEMO=false antes da primeira execução, com o banco vazio.
    2. Ajuste WEB_REDIRECT_URIS e CORS_ORIGINS com o endereço público, por exemplo https://loja.exemplo.com/callback.
    3. Suba o projeto e cadastre sua conta pela tela de entrada.
    4. Promova a conta a administrador no banco cesto_auth: 
      docker compose exec postgres psql -U cesto -d cesto_auth \
  -c "UPDATE users SET role = 'ADMIN' WHERE email = 'voce@empresa.com';"
    5. Saia e entre de novo para receber um token com os escopos de administrador.

    Acesso pela rede e HTTPS

    Coloque um proxy com HTTPS (Caddy, Traefik ou Nginx) na frente da porta APP_PORT. O contêiner web já encaminha /api, /oauth, /.well-known e /health para o gateway. O gateway confia nos cabeçalhos X-Forwarded-* para registrar o IP real e aplicar o rate limit por cliente.

    Guia das telas

    O que cada tela da loja e do painel mostra, o que dá para fazer nela e de qual serviço vêm os dados.

    Loja

    Lista os produtos ativos, cada um com a sua ilustração, seção, SKU, etiqueta de preço e saldo. Os dados vêm do catalog; o saldo de cada produto vem do inventory. Produtos sem estoque continuam visíveis, mas não podem ser adicionados ao carrinho.

    • Filtros laterais. Seções (categorias) com a contagem de produtos em cada uma, faixas de preço (até R$ 80, R$ 80 a R$ 200, acima de R$ 200) e a opção Só com estoque. Os filtros ativos aparecem como etiquetas que podem ser removidas uma a uma.
    • Busca. Por nome, descrição ou SKU. O atalho / leva direto ao campo de busca.
    • Ordenação. Chegaram agora, Nome (A a Z), Menor preço e Maior preço, com 12 produtos por página.
    • Guardar. O botão com o coração em cada produto guarda o item para depois (veja Guardados).
    • Estoque acabando. Com poucas unidades, o produto mostra Restam N (ou Última unidade).

    Visualização rápida do produto

    Clicar num produto abre um painel com a ilustração grande, a descrição, o SKU, o preço e o saldo. Ali dá para escolher a quantidade antes de adicionar ao carrinho e guardar o produto. Esc fecha o painel.

    Guardados

    Lista os produtos guardados com o botão Guardar, com preço e saldo atuais, o botão Adicionar ao carrinho em cada um e Pôr tudo no carrinho para a lista inteira. A lista fica no navegador (localStorage, chave cesto.guardados.<id do usuário>), separada por usuário: não vai para o servidor e não aparece em outro aparelho.

    Entrada e cadastro

    A tela de entrada faz o fluxo Authorization Code com PKCE: gera o code_verifier, envia o desafio S256 junto com o e-mail e a senha, recebe o código e troca pelo token. O cadastro cria um cliente e já faz o login.

    Carrinho

    O carrinho abre num painel lateral em formato de cupom: cada linha com miniatura, quantidade e subtotal, e o total no pé. Guardar para depois tira o item do carrinho e o coloca em Guardados. O carrinho (serviço cart, no Redis) guarda só o produto e a quantidade; preços e nomes são lidos do catálogo a cada consulta, então o cliente sempre vê o valor atual.

    Checkout

    O checkout tem três etapas, e dá para voltar a qualquer uma antes de confirmar:

    1. Entrega. Endereço. A tela lembra o último endereço usado neste navegador (chave cesto.endereco) e já o preenche.
    2. Pagamento. Pix, Cartão ou Boleto. Com Cartão dá para simular um cartão recusado.
    3. Revisão. Itens com miniatura, endereço, forma de pagamento e total. Confirmar cria o pedido (POST /api/v1/orders, resposta 202) e começa a saga.

    Pedidos

    Cada pedido mostra os itens com miniatura, o total e a trilha da saga: cada etapa com o horário e o serviço que cuidou dela (orders recebe o pedido, inventory reserva o estoque, payments cobra, orders confirma). Quando o pedido cai, a trilha mostra o motivo (falta de estoque, pagamento recusado, cancelamento). A tela se atualiza sozinha enquanto há pedidos em andamento.

    • Comprar de novo põe os mesmos itens no carrinho, com os preços atuais.
    • Cancelar aparece enquanto o pedido ainda não foi confirmado. A reserva de estoque volta para o saldo.

    Notificações

    Cada evento importante vira uma notificação: boas-vindas, pedido recebido, confirmado, cancelado, pagamento recusado, enviado e entregue. O sino mostra quantas ainda não foram lidas. Os dados vêm do serviço notifications.

    Administração

    Só aparece para administradores. No topo ficam os indicadores: receita confirmada, ticket médio, pedidos para enviar e produtos com estoque baixo.

    • Pedidos. A loja vê os pedidos de todos os clientes, filtra por status (por exemplo, Em andamento), marca cada um como enviado, entregue ou cancelado e exporta a lista em CSV.
    • Produtos e estoque. Busca por nome ou SKU, filtro estoque baixo (menos de 5 unidades disponíveis), alteração de preço, ativação e desativação e ajuste do saldo disponível. O cadastro de produto fica num bloco recolhível.

    Serviços

    Página pública, sem login, com a saúde de cada um dos oito serviços e do Redis. Os dados vêm de GET /health no gateway, que faz um ping no Redis e consulta o /health de cada serviço com limite de 2 s. A página mostra o estado de cada um, o tempo de resposta do gateway e o histórico das últimas 30 consultas. Ela se atualiza sozinha a cada 5 s, então serve para acompanhar um serviço que está subindo ou reiniciando.

    Tema escuro e atalhos

    O botão no cabeçalho alterna entre tema claro e escuro. Até a pessoa escolher, a interface segue o tema do sistema; a escolha fica no navegador (chave cesto.tema). Atalhos de teclado: / vai para a busca e Esc fecha painéis (carrinho, notificações, visualização rápida).

    No celular

    A interface se adapta a telas pequenas: a loja, os filtros, o carrinho, os pedidos e o painel funcionam no celular com os mesmos recursos da versão para computador.

    Caminho de uma requisição

    O gateway acrescenta um x-request-id que acompanha a requisição em todos os logs e volta na resposta. Rotas /internal/* nunca são expostas pelo gateway.

    A saga do pedido

    Caixas arredondadas são estados do pedido; caixas retas são os serviços que reagem aos eventos. As linhas tracejadas são os caminhos de falha.

    SituaçãoO que acontece
    Falta estoqueinventory.rejected cancela o pedido sem mexer no saldo
    Pagamento recusadopayment.declined cancela o pedido e order.cancelled devolve a reserva
    Cliente cancela antes do pagamentoO pedido é cancelado e a reserva volta para o saldo
    Loja cancela um pedido confirmadoO estoque baixado volta e o pagamento é estornado
    Pagamento aprovado depois do cancelamentoO pedido continua cancelado e o pagamento é estornado

    Outbox, deduplicação e novas tentativas

    MecanismoComo funciona
    OutboxO evento é gravado na tabela outbox_events na mesma transação da mudança. Um relay publica no Redis e marca como publicado. Se o Redis cair, nada se perde.
    DeduplicaçãoQuem consome grava o id do evento em processed_events na mesma transação do efeito. Entregas repetidas são ignoradas.
    Grupos de consumidoresCada serviço lê com XREADGROUP. Várias réplicas dividem o trabalho.
    Novas tentativasMensagem não confirmada é reivindicada com XCLAIM depois de 15 s. Depois de 5 entregas, vai para cesto:events:dead-letter com o motivo.
    Concorrência no estoqueA reserva usa UPDATE ... WHERE available >= quantidade numa transação, e o banco ainda impede saldo negativo com CHECK.

    Autenticação OAuth2

    Como a interface e os serviços obtêm tokens, e o que cada escopo libera.

    Fluxos suportados

    FluxoQuem usaDetalhes
    Authorization Code + PKCE (S256)Interface web (cesto-web, cliente público)Código de uso único, válido por 60 s, preso ao redirect_uri e ao desafio
    Refresh TokenInterface webRotação a cada uso; reuso de um token antigo revoga a família inteira
    Client CredentialsServiços (cesto-internal)Escopo internal, token em cache até 30 s antes de expirar

    Passo a passo do login

    1. O cliente gera um code_verifier aleatório e calcula code_challenge = BASE64URL(SHA256(verifier)).
    2. POST /oauth/authorize com client_id, redirect_uri, code_challenge, state, e-mail e senha. A resposta traz o code e o mesmo state.
    3. POST /oauth/token com grant_type=authorization_code, o code e o code_verifier.
    4. A resposta traz access_token (JWT, 15 min), refresh_token (30 dias) e os escopos concedidos.
    { "access_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6...", "token_type": "Bearer",
  "expires_in": 900, "refresh_token": "...",
  "scope": "orders:read orders:write cart:write notifications:read" }

    O endpoint de token aceita JSON ou application/x-www-form-urlencoded e responde erros no formato do RFC 6749 ({"error": "invalid_grant", "error_description": "..."}).

    Escopos e papéis

    EscopoClienteAdministradorLibera
    cart:writesimsimAlterar o carrinho
    orders:readsimsimVer pedidos e pagamentos
    orders:writesimsimFechar e cancelar pedidos próprios
    notifications:readsimsimNotificações
    catalog:writenãosimProdutos e categorias
    inventory:writenãosimAjustar estoque
    orders:managenãosimEnviar, entregar e cancelar qualquer pedido
    internalnãonãoRotas internas (só serviços)

    Cada rota declara no contrato o tipo de acesso (public, user, admin ou service) e os escopos exigidos. A verificação acontece antes do handler.

    Chaves e tokens

    • As chaves RSA de 2048 bits são geradas na primeira execução e guardadas em signing_keys. A chave pública fica em GET /oauth/jwks.
    • Os demais serviços validam os tokens com o JWKS (cache de 10 min), sem consultar o auth a cada requisição.
    • Senhas e segredos de cliente usam scrypt com sal aleatório. Códigos e refresh tokens são guardados só como SHA-256.
    • Códigos e tokens expirados são apagados a cada hora.

    Contratos e validação

    O pacote packages/contracts é a única fonte da verdade das rotas, dos DTOs e dos eventos.

    Os contratos são esquemas Zod em JavaScript. O mesmo esquema valida em tempo de execução a entrada e a saída de cada rota, gera o OpenAPI e alimenta o cliente HTTP usado pela interface, pelos serviços e pelo teste ponta a ponta. Não há tipos de compilação: quando ajuda a leitura, as funções têm comentários JSDoc leves (@param, @returns), que o editor usa para completar código.

    Auxiliares de DTO

    AuxiliarPara que serve
    paginated(schema)Esquema de página com items, page, pageSize, total e totalPages
    toPage(items, total, page, pageSize)Monta a página a partir de uma consulta
    envelope(schema)União discriminada { ok: true, data } ou { ok: false, error }
    success(schema) / failureOs dois lados do envelope, separados
    ok(value) / err(error)Retorno de sucesso ou falha sem exceção

    Contratos de rota

    Cada rota é declarada uma vez com defineEndpoint: método, caminho, resumo, tags, tipo de acesso e os esquemas de params, query, body e response. buildPath preenche os parâmetros do caminho (/orders/:id) e buildQuery monta a query string.

    export const api = {
  catalog: {
    getProduct: defineEndpoint({
      method: 'GET', path: '/api/v1/catalog/products/:id', summary: 'Detalhe do produto',
      tags: ['catalog'], auth: 'public', params: IdParams, response: ProductDto
    })
  }
};

route(app, api.catalog.getProduct, ({ params, principal }) =>
  catalog.get(params.id, isAdmin(principal)));

const product = await request(api.catalog.getProduct, { params: { id } });

    route valida params, query e body com Zod, converte tipos (?page=2 vira número), checa o token, o papel e os escopos, chama o handler, valida a saída e devolve no envelope. Campos extras são recusados (z.strictObject). Como não há compilador, essa validação em tempo de execução, mais os testes, é o que garante que o handler e o cliente concordam com o contrato.

    INSUFFICIENT_STOCK409Saldo insuficiente

    Erros do Prisma também são traduzidos: P2002 vira CONFLICT e P2025 vira NOT_FOUND.

    Eventos validados

    eventSchemas associa cada nome de evento a um esquema Zod. bus.publish('order.placed', payload) valida o payload antes de publicar, e o handler de bus.subscribe recebe o payload já validado. Na leitura, o envelope é validado de novo; payload inválido vai direto para a dead-letter.

    Convenções, todas as rotas públicas e exemplos com curl.

    Envelope e convenções

    • Base: http://localhost:8080 (pela interface) ou http://localhost:8000 (gateway direto).
    • Valores em centavos (priceCents, totalCents) e datas em ISO 8601.
    • Paginação com page e pageSize (máximo 100).
    • Documentação interativa em /api/docs e especificação em /api/openapi.json, geradas dos contratos.
    { "ok": true, "data": { "items": [ ... ], "page": 1, "pageSize": 20, "total": 16, "totalPages": 1 } }

{ "ok": false, "error": { "code": "VALIDATION_FAILED", "message": "Dados inválidos",
  "details": [ { "path": "pageSize", "message": "Too big: expected number to be <=100" } ],
  "requestId": "..." } }

    O .env.example também traz http://localhost:5173 em WEB_REDIRECT_URIS e CORS_ORIGINS, para a interface do npm run dev. Cada serviço valida a própria configuração com Zod ao iniciar (src/env.js) e para com uma mensagem clara se algo estiver faltando.

    Checklist para produção

    • Senhas fortes em DB_PASSWORD e SERVICE_CLIENT_SECRET (os scripts já geram).
    • SEED_DEMO=false e uma conta de administrador própria.
    • HTTPS na frente da interface, e WEB_REDIRECT_URIS / CORS_ORIGINS com o domínio real.
    • Gateway de pagamento real no lugar do simulado.
    • Backup diário dos seis bancos e persistência do Redis (o compose já liga o AOF).
    • Não publique a porta do gateway se só a interface for usada. A página Serviços e o /health são públicos; se não quiser expor o estado interno, bloqueie /health no proxy.

    Personalizar e estender

    Onde mexer para acrescentar rotas, eventos, serviços e um provedor de pagamento.

    Adicionar uma rota

    1. Declare o contrato em packages/contracts/src/api.js, reaproveitando ou criando esquemas em domains/.
    2. Registre no serviço: route(app, api.catalog.novaRota, handler).
    3. Reinicie o serviço (o npm run dev recarrega sozinho). Não há compilação: o handler, o cliente da interface e o OpenAPI passam a conhecer a rota na hora.

    Adicionar um evento

    1. Acrescente o esquema em eventSchemas (packages/contracts/src/events.js).
    2. No serviço que publica, grave no outbox dentro da transação: outbox(tx, createEnvelope('nome.evento', payload)).
    3. No serviço que consome, inclua o handler em bus.subscribe({ 'nome.evento': ... }) usando a deduplicação por processed_events.

    Adicionar um serviço

    1. Copie um serviço parecido em services/ e troque o nome no package.json.
    2. Se tiver banco, crie cesto_novo em docker/postgres/init.sql, ajuste o schema.prisma e gere a migração com npx prisma migrate dev dentro da pasta do serviço.
    3. Inclua o serviço na lista de workspaces, em scripts/dev.mjs, scripts/generate.mjs e scripts/migrate.mjs.
    4. Adicione o bloco no docker-compose.yml e o prefixo em services/gateway/src/routes.js.

    Trocar o pagamento simulado

    /** @implements {PaymentGateway} */
export class MeuProvedor {
  name = 'meu-provedor';
  /** @param {ChargeRequest} request @returns {Promise<ChargeResult>} */
  async charge(request) { ... }
  /** @param {string} reference @param {number} amountCents */
  async refund(reference, amountCents) { ... }
}

    A classe precisa ter name, charge e refund, como o SimulatedGateway de services/payments/src/gateway.js. Troque new SimulatedGateway(...) por new MeuProvedor(...) em services/payments/src/main.js. A chave de idempotência enviada é o id do pedido.

    Imagens, marca e interface

    • Produtos aceitam imageUrl (caminho ou URL de até 500 caracteres). Sem ele, a interface procura apps/web/public/produtos/<slug>.svg; se não achar, mostra um espaço neutro.
    • Para trocar uma ilustração, substitua o SVG do slug. O gerador das 16 ilustrações fica em .design/ilustracoes/gerar.py.
    • As cores da interface, nos dois temas, ficam em variáveis no topo de apps/web/src/styles.css.
    • As fontes ficam em apps/web/public/fonts, com os arquivos de licença OFL.
    • A logo fica em docs/images/logo.svg e apps/web/public/favicon.svg.
    • Os manuais em PDF são gerados de docs/fonte/ com node docs/fonte/gerar_pdfs.mjs (requer o Playwright com o Chromium).

    Testes e qualidade

    O que cada comando de teste cobre e o que a integração contínua executa.

    Testes automatizados

    ComandoO que cobre
    npm testContratos (URLs, DTOs, esquemas, eventos), núcleo HTTP (validação, envelope, JWT, papéis, escopos, mapeamento de erros), outbox, saga e preços, PKCE e escopos, carrinho, notificações
    TEST_REDIS_URL=... npm testInclui o barramento com Redis real: entrega, confirmação e nova tentativa
    npm run checknode --check em todos os arquivos .js e .mjs de packages/, services/ e scripts/ (erros de sintaxe)
    npm run smoke21 verificações ponta a ponta com a API rodando

    Sem compilador, os erros que o TypeScript pegava antes aparecem agora nos testes e na validação dos contratos em tempo de execução. Rode npm test antes de cada commit.

    Integração contínua

    A cada push na main e a cada pull request, o GitHub Actions (.github/workflows/ci.yml, Node.js 22) instala as dependências com npm ci --ignore-scripts, gera os clientes Prisma (npm run generate), constrói a interface (npm run build, que só existe em apps/web), roda npm run check e os testes com PostgreSQL e Redis reais, cria os bancos com docker/postgres/init.sql, aplica as migrações, sobe os oito serviços com npm run start:local, executa o teste ponta a ponta (npm run smoke) e constrói as duas imagens Docker. Os serviços não têm etapa de compilação.

    Onde olhar

    • A página Serviços e o GET /health no gateway mostram o Redis e cada serviço.
    • Os logs são JSON com service e reqId; filtre pelo x-request-id da resposta.
    • No Redis, XINFO GROUPS cesto:events:order.placed mostra as pendências por serviço.
    • No banco, SELECT * FROM outbox_events WHERE published_at IS NULL mostra os eventos que ainda não saíram.
